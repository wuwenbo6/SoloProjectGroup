# 大规模基因序列比对后端服务

基于 Go + gRPC + RabbitMQ + Redis 构建的分布式基因序列比对系统。

## 系统架构

```
┌─────────────┐
│  HTTP API   │  文件上传、状态查询、结果下载
└──────┬──────┘
       │
┌──────▼──────┐
│  调度器     │  任务分发、结果归并
└──────┬──────┘
       │
┌──────▼──────┐
│  RabbitMQ   │  任务队列
└──────┬──────┘
       ├─────────────┬─────────────┐
┌──────▼──────┐┌────▼─────┐┌──────▼──────┐
│  Worker 1   ││  Worker 2 ││  Worker 3   │  并行执行比对
└──────┬──────┘└──────┬────┘└──────┬──────┘
       └──────────────┼──────────────┘
                      │
               ┌──────▼──────┐
               │    Redis    │  缓存热点序列、任务状态
               └─────────────┘
```

## 核心功能

### 1. Needleman-Wunsch 序列比对算法
- 全局序列比对
- 优化空间复杂度（O(min(m,n))）
- 回溯获取比对结果
- 计算一致性百分比

### 2. 文件切片与并行处理
- 支持最大 1GB FASTA 文件上传
- 自动切分为 100MB 切片
- 分发到多个 Worker 节点并行处理

### 3. 调度器模块
- RabbitMQ 消息队列
- 任务重试机制（最多 3 次）
- 结果归并

### 4. Worker 管理
- 心跳检测
- 动态扩缩容（Docker replicas）
- 任务负载均衡

### 5. Redis 缓存
- 缓存热点序列比对结果
- 任务状态存储
- Worker 节点注册信息

## 快速开始

### 使用 Docker Compose（推荐）

```bash
# 启动所有服务
make docker-up

# 停止服务
make docker-down
```

### 本地开发

1. 安装依赖：
```bash
# 启动 Redis
docker run -d -p 6379:6379 redis:7

# 启动 RabbitMQ
docker run -d -p 5672:5672 -p 15672:15672 rabbitmq:3-management
```

2. 运行服务：
```bash
# 启动 API 服务器
make server

# 启动 Worker（另一个终端）
make worker
```

## Bug 修复：任务超时与死信队列

### 问题
当同时提交10个以上大文件任务时，RabbitMQ队列堆积导致部分任务超时（30分钟）后被worker丢弃，但前端状态仍显示"处理中"。

### 解决方案

1. **死信交换器 (DLX) + 死信队列**
   - 创建 `alignment_dlx` 交换器和 `alignment_deadletter` 队列
   - 超时或被拒绝的消息自动路由到死信队列
   - 调度器消费死信队列并重试任务

2. **消息 TTL 设置**
   - 队列级别 TTL: 30分钟
   - 消息级别 TTL: 根据重试次数递减（避免无限重试）
   - Worker端执行超时: 25分钟

3. **智能重试机制**
   - 最多重试 3 次
   - 每次重试后 TTL 递减（防止队列堆积）
   - 超过最大重试次数后标记任务为 FAILED

4. **状态一致性保证**
   - 超时任务及时更新状态为 FAILED
   - 前端可查询到正确的任务状态和错误信息
   - 任务状态变更记录在 Redis 中

### 相关配置常量
```
MessageTTL  = 30 * 60 * 1000  // 消息队列TTL: 30分钟
TaskTimeout = 25 * 60 * 1000  // Worker执行超时: 25分钟
MaxRetries  = 3                // 最大重试次数
```

## Bug 修复：结果归并内存溢出（外部归并排序）

### 问题
当处理大量短序列（长度<50）时，N个序列会产生 N*(N-1)/2 个比对结果。原来的实现一次性加载所有结果到内存再排序，导致内存溢出（OOM）。

例如：
- 1000个序列 → 499,500个比对结果
- 5000个序列 → 12,497,500个比对结果
- 每个结果约500字节 → 约6GB内存占用

### 解决方案：外部多路归并排序

1. **分块预先排序**
   - 每个Worker完成chunk比对后，按Score降序排序结果
   - 结果以JSON Lines格式写入临时文件（`/temp/chunk_{id}.jsonl`）
   - 每个chunk结果独立存储，不占用主内存

2. **多路归并算法**
   - 使用最小堆（按Score降序）实现K路归并
   - 同时打开所有临时文件，每次只读取堆顶元素
   - 内存占用 = K * 单个结果大小（K = chunk数量）

3. **内存限制机制**
   - 热力图生成限制：Top 1000 结果
   - 最终结果限制：Top 100,000 结果
   - 流式处理避免全量加载

4. **自动清理机制**
   - 归并完成后异步删除临时文件
   - 临时目录隔离防止冲突

### 架构对比

**改进前（内存排序）**
```
Worker1 → [结果] \
Worker2 → [结果] → 全部加载到内存 → 排序 → 热力图 → 保存
...
WorkerN → [结果] /
内存占用: O(N²)
```

**改进后（外部归并）**
```
Worker1 → [结果排序] → temp/chunk_0.jsonl \
Worker2 → [结果排序] → temp/chunk_1.jsonl → 多路归并(堆) → 流控输出 → 保存
...
WorkerN → [结果排序] → temp/chunk_N.jsonl /
内存占用: O(K)  K = chunk数量
```
